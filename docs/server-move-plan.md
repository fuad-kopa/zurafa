# Переезд онлайн-части Зурафы на свой сервер — план на утверждение

Дата: 2026-10-12. Сервер проверен только чтением: Contabo `13.140.155.127`, Debian 13, нагрузка 0,1,
свободно 10 ГБ памяти и 178 ГБ диска. Соседи: gorselstar (порт 3000) и ahiska (порт 3001), каждый в своём
docker compose, nginx-файлы `gorselstar.conf` и `ahiska.conf`, бэкапы в 03:30 и 03:45.

## Что решаем

| # | Уязвимость | Как закрывает сервер |
|---|---|---|
| 1 | Рейтинг считает браузер, игрок может записать себе любой | Рейтинг онлайн-партий считает только сервер (Glicko-2), Supabase запрещает клиенту менять поле `rating` |
| 2 | Время на часах в онлайне сообщает сам игрок | Часы идут на сервере: время хода меряет сервер по своим часам |
| 3 | Часть пар не соединится напрямую (P2P без ретранслятора) | Ходы идут через сервер по WebSocket; P2P остаётся запасным |

Плюс к наплыву: подбор случайного соперника, таблица лидеров и сбор ошибок со стеком.

## Что не меняется

- **Сайт остаётся на GitHub Pages.** Это CDN Fastly, переживёт наплыв лучше одного сервера, и если сервер
  упадёт, сайт и игра с компьютером продолжат работать. После сегодняшней правки новый посетитель тянет
  ~1,5–2 МБ, лимит Pages (100 ГБ в месяц) — это 50–60 тысяч новых посетителей в месяц. Если упрёмся — статику
  переносим на сервер за вечер (rsync + nginx), это шаг 6.
- **Аккаунты остаются в Supabase.** Сервер проверяет токен Supabase и узнаёт игрока; переносить пользователей
  не нужно.
- **Next.js не нужен.** Сайт — Vite + TypeScript без фреймворка; серверу нужен WebSocket и база, это
  маленький Node-сервис. Next ничего не добавит, только вес.

## Устройство

```
zurafa.app            → GitHub Pages (как сейчас)
api.zurafa.app        → nginx (общий) → 127.0.0.1:3100 → контейнер zurafa-server (Node 22, ws)
                                                          └ контейнер zurafa-db (PostgreSQL 16, свой том)
Supabase              → только вход и профили; сервер читает токены, пишет рейтинг сервисным ключом
```

Изоляция от gorselstar и ahiska:
- папка `/root/prod/zurafa`, compose-проект `zurafa`, свой `.env` (секреты вписываете вы сами, не через чат);
- порт 3100 только на 127.0.0.1; лимиты контейнеров: 1 ГБ памяти, 2 CPU;
- свой файл `/etc/nginx/sites-available/zurafa-api.conf`, чужие файлы не трогаю; перед каждым `reload` — `nginx -t`;
- свой сертификат certbot для `api.zurafa.app` через общий webroot;
- бэкап базы в 04:00 в `/root/backups/zurafa`.

## Шаги

**Шаг 0 — вы (10 минут):**
1. У регистратора домена (Porkbun) добавить запись `A api.zurafa.app → 13.140.155.127`.
2. Сказать мне «да» этому плану.

**Шаг 1 — я, на ноутбуке, без сервера (2–3 дня):**
код `server/` в репозитории — комнаты по ссылке через сервер, ходы проверяет наш движок, часы на сервере,
переподключение после обрыва, зрители, реванш, очередь подбора соперника, Glicko-2, таблица лидеров,
`/api/errors`, `/api/health`. Нагрузочный тест: 2 000 одновременных партий на ноутбуке.

**Шаг 2 — я, на сервере, ~1 час, соседи не останавливаются:**
папка, compose, nginx-файл, сертификат, запуск. Проверка: `curl api.zurafa.app/api/health`,
`docker ps` у gorselstar и ahiska без изменений.

**Шаг 3 — переключение клиента:** онлайн-игра сначала пробует сервер, при недоступности — P2P как сейчас.
Таблица лидеров и «Играть со случайным соперником» появляются на сайте.

**Шаг 4 — закрыть рейтинг в Supabase:** миграция, после которой клиент не может менять `rating`
(SQL выполнить в панели Supabase → SQL Editor; текст дам готовым).

**Шаг 5 — эксплуатация:** проверка здоровья раз в минуту, ротация логов, копия бэкапа вне сервера.

**Шаг 6 — по необходимости:** статика на сервер + Cloudflare перед ним (если упрёмся в лимит Pages).

## Риски

- Сервер один: если он упадёт, онлайн по ссылке уйдёт на P2P, рейтинговые партии и подбор временно не работают;
  сайт и игра с компьютером — работают.
- Нагрузка: одна партия — это несколько сообщений в минуту; 11 ГБ памяти хватит на десятки тысяч соединений.
  Узкое место скорее сеть порта Contabo, но ходы весят байты.
